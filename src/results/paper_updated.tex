% ── Abstract ─────────────────────────────────────────────────────────────────
\begin{abstract}
Agentic microservices introduce adaptive reasoning and tool orchestration,
but also new fault surfaces that are difficult to validate using conventional
microservice testing. This paper presents a controlled fault-injection study
across nine instrumented agent services in the LLM-MAS architecture and
evaluates fault reachability, infection, and propagation using
data-flow observation-point tracing (Laski-Korel-Weyuker+RIP, hereafter LKW+RIP~\cite{lkw,rapps-weyuker}). We execute two benchmark suites
(Google-bench and Retail-bench) on Concordia SPEED HPC and map observed
failures to MAST-style fault categories. The experimental protocol separates
three roles: B1 deterministic oracle specification, B2 live-LLM natural
variance, and B3 live-LLM mutant execution. We report both full-pipeline and
agent-level evidence. In the full checkout pipeline, B3 execution across four
model configurations yields 29 killed mutants out of 40 total
(72.5\% mutation score). A strong model-behaviour effect emerges: the larger
\texttt{qwen2.5-coder:14b} configuration frequently short-circuits the ReAct
tool loop and produces false negatives, whereas \texttt{qwen2.5:3b} preserves
tool execution and detects most injected faults. Per-benchmark root cause
analysis shows that FM-2.2 (hallucinated output) is the highest-risk fault
class at both single-agent and cross-agent boundaries, completing all
checkpoints with zero structural loss while silently corrupting downstream
state. We provide automated HITL tier classification and inter-agent
propagation evidence to identify which faults are silently absorbed, which
propagate to business-harmful states, and which require human intervention.
The main practical conclusion is architectural: LLM-MAS deployments require
checkpoint-level semantic validation at inter-agent boundaries, not only
step-level workflow monitoring.
\end{abstract}

\section{Introduction}
% ═════════════════════════════════════════════════════════════════════════════

Agent-driven microservices combine tool-calling, reasoning loops, and external
side effects (e.g., carrier selection, tracking generation, persistence). While
this increases autonomy, it can introduce latent failures not captured by unit
or API tests. Our goal is to evaluate whether controlled faults can be injected,
reproduced, observed, and contained before they become business harm.

This study covers nine agent services from the Google Online Boutique
e-commerce application. Six are full Python ReAct agents. Two
(CartService in C\#, CheckoutService in Go) are exercised via thin Python
wrappers that share the same instrumentation schema. One is the shipping
orchestration path.

We evaluate all nine using a three-baseline protocol.
\textbf{B1} runs each agent without a live LLM and records the correct
deterministic output --- the ground truth.
\textbf{B2} runs with a live LLM and no fault injected, measuring how
much the output naturally varies across repeated runs.
\textbf{B3} runs with a live LLM and a specific fault active, then
judges whether the fault caused a detectable deviation beyond the B2
noise envelope.

We run two evaluation modes. In \emph{standalone} mode each agent is
tested in isolation to measure local fault detectability; each agent
receives a synthetic task description constructed to match its expected
input contract (e.g., CurrencyAgent receives a fixed cart total and
target currency pair, mirroring the output the orchestrator would
produce in full-pipeline mode). In \emph{full-pipeline} mode
(\emph{full checkout orchestration}: the end-to-end sequence in which
all agent services execute in order to complete a customer purchase)
all agents run end-to-end to measure whether a fault in one agent
silently corrupts a downstream agent's output.

In this project, we answer the following research questions:
\begin{description}
  \item[\textbf{RQ1}] Can realistic faults be injected into an agent-driven
        service and reliably reproduced?
  \item[\textbf{RQ2}] Where does failure first appear in the execution flow?
  \item[\textbf{RQ3}] How far does it propagate downstream?
  \item[\textbf{RQ4}] Which failures can be auto-resolved by agents, and which
        require human intervention?
  \item[\textbf{RQ5}] How stable are these observations across repeated runs in
        a controlled compute environment?
  \item[\textbf{RQ6}] Can policy-based boundary recovery contracts reduce the
        manual intervention burden for silent and flag-detectable faults
        (Tier~2 and Tier~3, defined in Section~\ref{sec:lkw-signatures}),
        and can their application be verified at execution level?
\end{description}

\section{Related Work}
\label{sec:related}
% ═════════════════════════════════════════════════════════════════════════════

\paragraph{Chaos engineering and infrastructure fault injection}
Chaos Monkey~\cite{netflix-chaos} and the Netflix Simian Army introduced
random instance termination as a reliability discipline for cloud services.
LitmusChaos~\cite{litmuschaos} and ChaosMesh~\cite{chaosengineering} extended
this to Kubernetes-native experiments covering pod deletion, CPU stress, network
partition, and I/O latency. Istio fault injection~\cite{istio} injects HTTP
delays and aborts at the sidecar proxy layer. All of these tools operate at the
\emph{infrastructure and network} level: they can terminate a process or drop a
packet, but they cannot inject a semantically plausible data-corruption fault
(e.g., a hallucinated product ID or an inflated currency amount) into a running
LLM reasoning loop. LKW+RIP operates at the \emph{application} level: faults
are injected into the Python execution path of agent business logic, and
checkpoints record the semantic state at meaningful computation boundaries
rather than at OS or network events.

\paragraph{LLM agent benchmarking and reliability}
AgentBench~\cite{agentbench} evaluates LLM agents across interactive
environments (web browsing, coding, game) using success rate as the primary
metric, but does not instrument intermediate reasoning state or propagation
depth. ToolBench / ToolLLM~\cite{toolbench} evaluates tool-calling accuracy
for single-agent systems. Neither framework provides per-checkpoint execution
traces that would enable RIP-style root cause localisation.
Reliability surveys of LLM-based agents~\cite{agentreliability} categorise
failure modes (refusal, hallucination, tool misuse) from observed outputs but
do not perform controlled injection. Our work differs: we inject specific fault
modes with known ground truth and measure their propagation through a
multi-agent pipeline, enabling causal attribution at the agent boundary level.

\paragraph{Multi-agent system failure taxonomy}
MAST~\cite{mast} proposes a taxonomy of failures in multi-agent systems
covering specification, design, and execution layers. We adopt MAST fault
class identifiers (FM-1.x, FM-2.x, FM-3.x, BL-*) as our injection vocabulary,
mapping each category to a concrete Python-level injection function.
MAST characterises failures at the \emph{classification} level but leaves two
operational gaps: (1) it does not specify how to instrument an LLM-MAS execution
to distinguish Tier~3 silent faults (FM-2.2) from structurally correct runs ---
because all checkpoints complete normally even when values are corrupt; and
(2) it does not address cross-boundary propagation, where a structurally
correct but semantically wrong output from agent~A silently corrupts
agent~B with no observable signal at either hop.
This work fills both gaps: the LKW placement taxonomy (P1--P5) provides the
instrumentation criterion for gap~(1), and the cross-agent boundary contract
layer provides the detection and containment mechanism for gap~(2).

\paragraph{LLM output validation and guardrails}
NeMo Guardrails~\cite{nemoguar} and Guardrails AI~\cite{llmguardrails} provide
format and content validation of LLM responses at the model boundary using
Colang rules or Pydantic validators. These approaches validate the output of a
single LLM call; they are not designed to validate \emph{inter-agent handoffs}
where the observed payload from one agent becomes the input of another. Our
boundary contracts extend the guardrail concept to the agent-to-agent data
plane: a \texttt{boundary\_contract()} call compares expected and observed
payloads at every architectural handoff point and triggers a recovery policy
decision before propagation occurs. This complements model-boundary guardrails
with a system-level safety layer.

\paragraph{Multi-agent orchestration frameworks and testing}
LangGraph~\cite{langgraph} provides a state-machine execution model for
multi-agent workflows; AutoGen~\cite{autogen} enables multi-agent conversation
patterns. Neither framework includes built-in fault injection tooling or
inter-agent data validation contracts. Testing methodologies for LLM-based
multi-agent systems are nascent: existing work focuses on functional output
evaluation~\cite{agenteval} rather than on characterising failure propagation
across agent boundaries. Our study addresses this gap by providing a complete
test infrastructure (LKW instrumentation, RIP analyser, HITL classifier,
boundary contract layer, and recovery policy engine) validated on two
LangGraph-based benchmarks. The infrastructure is applicable to any
LangGraph-based MAS that exposes named tool-call boundaries where
checkpoint instrumentation can be placed.

\paragraph{Fault propagation in distributed systems}
The concept of propagation depth originates in the Laski-Korel-Weyuker (LKW)
data flow testing criterion~\cite{lkw,rapps-weyuker} and the PIE
(Propagation, Infection, Execution) model~\cite{pie}. In distributed
systems, fault propagation is addressed through circuit breakers~\cite{netflix-chaos}
and bulkhead patterns that prevent one failing service from saturating its
caller. These mechanisms detect propagation via timeout and error-rate signals,
not via semantic state deviation. Our work applies the PIE model at the
\emph{agent reasoning} level --- tracking how a semantically corrupt value
(not a timeout) moves silently through a multi-agent pipeline --- which is a
distinct and underexplored problem class in the LLM-MAS reliability literature.

\paragraph{Human-in-the-loop systems}
Amershi et al.~\cite{hitlsurvey} survey HITL workflows in machine learning,
focusing on annotation, active learning, and model uncertainty. Our HITL tier
classification serves a different purpose: it characterises the
\emph{detectability effort} required for a human operator to identify and
intervene after a fault has been injected, using LKW checkpoint evidence rather
than model confidence scores. The three-tier system (structural $\to$
flag-detectable $\to$ silent) provides an operational metric that can guide
human review prioritisation and define SLA boundaries for automated recovery
policies.

\subsection{Google Online Boutique Application}
\label{sec:google-boutique}

The \emph{Google Online Boutique}~\cite{google-ob} is an open-source,
cloud-native e-commerce reference application comprising ten
interdependent microservices: \texttt{Frontend}, \texttt{CheckoutService},
\texttt{CartService}, \texttt{ProductCatalogService},
\texttt{CurrencyService}, \texttt{PaymentService},
\texttt{ShippingService}, \texttt{RecommendationService},
\texttt{EmailService}, and \texttt{AdService}.
Services communicate over gRPC with protobuf-encoded contracts and are
deployed on Kubernetes.  The application provides a realistic multi-service
call graph for a complete retail checkout that exercises monetary computation
(currency conversion, payment), catalogue lookup, personalisation
(recommendations, ads), fulfilment (shipping), and notification (email).
All seven services exercised in this study are drawn directly from this
benchmark; their gRPC interface contracts are defined in
\texttt{protos/demo.proto}.

\subsection{Benchmark Configurations}
\label{sec:bench-configs}

Three distinct benchmark configurations are used throughout the study,
differing in the LLM model and the set of agents exercised:

\begin{description}
  \item[\textbf{Google-bench}]
      Full checkout orchestration using \texttt{qwen2.5:3b} on Concordia
      SPEED HPC across three temperature settings (0.0, 0.7, 1.0). This is
      the \emph{tool-faithful evaluation} setting used for B2 natural
      variance and for the strongest B3 mutation-detection results.

  \item[\textbf{Retail-bench}]
      Full checkout orchestration using \texttt{qwen2.5-coder:14b} on
      Concordia SPEED HPC (A100-class GPU allocation). This is the
      \emph{large-model comparison} setting and is used to measure how a
      stronger code-capable model behaves under the same mutant suite.

    \item[\textbf{Agent-level checkout campaign}]
      Standalone live-LLM execution for the currently reported checkout-path agent roles
      (currency, payment, email, shipping\_quote, ship\_order) plus B1
      deterministic oracles. This configuration isolates checkpoint-level
      detectability at the single-agent boundary without downstream pipeline
      masking.
\end{description}

\subsection{Agentification Design}
\label{sec:agentification}

Each microservice is paired with a dedicated \emph{agent wrapper} (green
nodes in Figure~\ref{fig:architecture}) that implements the
LLM-directed orchestration layer.  All wrappers follow a uniform
\emph{ReAct}~\cite{react} pattern:
\begin{enumerate}
  \item The LLM receives a structured task description and a manifest of
        available tools (one deterministic tool function per microservice
        operation).
  \item It emits a sequence of \texttt{Thought / Action / Observation}
        steps until it produces a \texttt{Final Answer}.
  \item Each \texttt{Action} is dispatched to a \textbf{deterministic tool
        function} (e.g., \texttt{convert\_currency()},
        \texttt{validate\_card()}) that executes the microservice business
        logic without LLM involvement and returns a structured result.
        These are ordinary Python functions --- not agents --- and always
        produce the same output for the same input.
  \item The result is appended as an \texttt{Observation} and the loop
        continues.
\end{enumerate}
This design isolates LKW checkpoints at tool-function call boundaries ---
well-defined definition and use sites that are independent of LLM token
sampling --- while still exercising the full LLM reasoning path for
reachability and propagation measurement.

Not all nine services are implemented in Python.
Table~\ref{tab:agent-impl} lists the implementation type for each service.
Six services are full Python ReAct agents with LangGraph execution graphs
and native LKW instrumentation.
\texttt{CartService}~(C\#) is exercised via a thin Python mirror
(\texttt{co\_helper\_cart.py}) that reproduces the cart business logic and
the same checkpoint schema.
The \texttt{CheckoutService}~(Go) is covered by two Python sub-agent
wrappers for the quote and order paths.
All nine share the same ReAct loop structure, tool manifest format, and
LKW checkpoint schema, so the fault injection and oracle comparison
pipeline treats them uniformly.

\section{LKW and RIP Checkpoint Design}
\label{sec:lkw-design}
% ═════════════════════════════════════════════════════════════════════════════

This section defines how the LKW data-flow testing criterion is applied
to agent workflows: where to place observation checkpoints, what to
record at each point, and how to classify fault signatures.
These definitions are the shared vocabulary for all B1, B2, and B3
measurements in the paper.

\subsection{RIP Metrics and Definitions}


For each run, we record the checkpoint sequence and compute:
\begin{itemize}
  \item \textbf{Reachability}: checkpoints reached under the fault mode.
  \item \textbf{Infection point}: first checkpoint with semantically deviant
        data.
  \item \textbf{Propagation depth}: number of downstream steps absent in the
        fault trace.
  \item \textbf{Steps lost}: checkpoints present in the baseline but missing
        in the faulty run.
\end{itemize}

Let $B$ be the baseline checkpoint set and $F$ the faulty checkpoint set:
\begin{equation}
  \mathrm{StepsLost} = B \setminus F
\end{equation}
\begin{equation}
  \mathrm{PropagationDepth} = \lvert B \setminus F \rvert
\end{equation}

\subsection{Data Flow Observation Points (LKW)}

The instrumentation framework adapts the \emph{Laski-Korel-Weyuker} (LKW)
data flow testing criterion~\cite{lkw,rapps-weyuker} to agentic workflows.
In data flow testing, a program is instrumented at \emph{definition} (def)
sites where a variable receives a value and at \emph{use} sites where the
value determines computation (c-use) or control flow (p-use). A test suite
is adequate under a given criterion if it exercises every required def-use
pair for each variable under test.

We apply this framework to agent state variables --- monetary amounts, product
ID lists, carrier selections, tracking IDs, and boolean flag fields --- by
placing named observation points at the corresponding def and use sites within
the agent's LangGraph execution graph.

\paragraph{Variable selection criterion.}
A variable is selected as an LKW observation point if all three of the
following hold: (1)~it is the primary output of an agent's tool-function call
(the value the LLM acts on next); (2)~its value flows downstream --- either
to another agent or to a side-effecting operation (persistence, payment,
email); and (3)~its corruption would produce quantifiable business harm
(financial loss, incorrect recommendation, lost shipment). This gives one
primary LKW observation point per agent per tool call. Secondary points
are added at predicate-use (flag) sites per the All-DU-Paths criterion
for high-risk monetary and identifier variables (see §\ref{sec:placement-taxonomy}).

Each observation point records a \textbf{step name} (identifying the def or
use site), a \textbf{data payload} (the observed value of the guarded
variable, deep-copied at recording time), and a \textbf{timestamp}. The
ordered sequence of observation points for a single agent run forms the
\emph{LKW trace}, which is the primary evidence object for all RIP
(Reachability, Infection, Propagation) measurements.

The instrumentation is:
\begin{itemize}
  \item \textbf{Additive} --- observation points are injected alongside
        business logic without modifying control flow.
  \item \textbf{Non-intrusive} --- points write to an in-memory list and
        return immediately; no synchronous I/O on the hot path.
  \item \textbf{Data-preserving} --- the guarded value is deep-copied at
        recording time so post-hoc mutation cannot alter evidence.
\end{itemize}

\subsection{Checkpoint Placement Taxonomy and Coverage Criterion}
\label{sec:placement-taxonomy}

\paragraph{Coverage adequacy criterion.}
This study applies the \textbf{All-Uses} data-flow adequacy
criterion~\cite{rapps-weyuker} as its primary coverage standard: for every
guarded agent state variable, the LKW checkpoint sequence must include at
least one observation at each \emph{definition} site (P1) and at each
reachable \emph{computation-use} (c-use: P2, P3) and
\emph{predicate-use} (p-use: P4) site.  For high-risk monetary and
identifier variables (e.g., \texttt{amount}, \texttt{nanos},
\texttt{product\_ids}), the stricter \textbf{All-DU-Paths} criterion is
additionally applied, requiring every acyclic def-to-use path to be
exercised.

Five placement classes implement this criterion.
\textbf{P1}~(Pre-call) records the incoming payload at the definition site,
establishing reachability and the input baseline.
\textbf{P2}~(Post-computation) records the business-logic result after the
core transformation, enabling infection detection for data-corruption faults.
\textbf{P3}~(Post-side-effect) records the outcome of irreversible operations
(persistence, payment charge, email send), enabling propagation-depth
measurement for workflow-skip faults.
\textbf{P4}~(Post-metadata) records policy or flag fields appended after
primary logic, enabling Tier-2 p-use flag detection.
\textbf{P5}~(Terminal) records the value returned to the caller at the agent
handoff boundary, enabling cross-agent propagation comparison.

\subsection{Agent Checkpoint to Microservice Observation Point Mapping}
\label{sec:checkpoint-alignment}

The LKW checkpoints live in the agent layer; the deterministic microservices
do not have them.
For each agent checkpoint there is a corresponding observation point in the
original microservice --- typically the gRPC request or response value at
the analogous call site.
Table~\ref{tab:ckpt-align} makes this mapping explicit for all nine agents.

\subsection{Infection Point: Formal Definition}
\label{sec:infection-def}

Let $\langle C_1, C_2, \ldots, C_n \rangle$ be the ordered checkpoint sequence
of a given agent execution under fault mode $m$, and let $d_i$ denote the data
payload recorded at checkpoint $C_i$. Let $\hat{d}_i$ denote the corresponding
baseline (fault-free) value recorded during the NONE run for the same scenario.

The \textbf{infection point} is the earliest checkpoint at which the recorded
data deviates from baseline:
\begin{equation}
  I_m = \min_{i} \bigl\{C_i \;:\; d_i \neq \hat{d}_i \bigr\}
  \label{eq:infection}
\end{equation}
where $\neq$ is evaluated structurally (missing keys, type mismatches, list
length change) for P1--P3 checkpoints, and by flag value for P4 checkpoints.
If $F \subset B$ (steps are lost), infection is inferred from the first missing
step; the infection point is reported as the first absent checkpoint.

\subsection{Per-Failure-Type LKW Signature}
\label{sec:lkw-signatures}

Different fault classes leave different fingerprints in the LKW trace.
The fingerprint determines both where the infection point is (RQ2) and
how much effort a human needs to detect it (RQ4).

In practice, all fault classes reduce to three trace patterns, which we
call tiers.
\textbf{Tier~1 --- structural} (FM-3.1): steps are removed entirely
($F \subsetneq B$). The missing checkpoint is the infection signal.
Auto-detectable from step telemetry alone.
\textbf{Tier~2 --- flag} (FM-1.2 and BL-* workflow faults): all steps
execute, but a boolean diagnostic field at a P4 checkpoint is set.
Detectable by checking the flag value against B1.
\textbf{Tier~3 --- silent} (FM-2.2, FM-2.5, and BL-* data faults): all
steps execute, no flag fires. The only signal is a numeric or semantic
payload difference at a P2 checkpoint, visible only by comparison
against the B1 oracle.

\paragraph{Key design insight.}
Propagation depth alone is \emph{insufficient} to detect Tier~2 and
Tier~3 faults: both complete all steps, so
$\mathrm{PropagationDepth} = 0$.
A Tier~2 fault is visible only by reading the P4 flag field.
A Tier~3 fault is visible only by comparing the P2 payload against the
B1 oracle value.
This is why the checkpoints record guarded data, not just step presence.
Without payload recording, silent corruption (e.g., a hallucinated
currency amount) would produce a trace indistinguishable from a clean run.

The evidence from running all nine agents confirms this framework
produces stable, cross-service signatures: FM-2.2 (hallucination) maps
to a P2 c-use checkpoint across every agent, always at Tier~3, with no
step loss and deviation visible only in the payload.

\subsection{Fault Taxonomy and Mutation Operators}
\label{sec:fault-taxonomy}

Each injected fault is a \emph{mutation operator}~\cite{lkw} on a
specific agent state variable. The idea is straightforward: inject a
known change into one agent, run it with a live LLM, and check whether
the LKW checkpoints catch the deviation from the B1 oracle.

A fault that produces a detectable deviation is a \textbf{killed mutant}.
A fault whose trace stays inside the B2 natural-variance envelope is a
\textbf{live mutant} --- the fault was present, but the LLM did not
expose it.

The four general fault classes each target a different part of the trace.
\textbf{FM-3.1} removes steps --- the agent terminates before completing
its workflow.
\textbf{FM-1.2} mis-routes the workflow --- the agent takes the wrong
action branch.
\textbf{FM-2.2} fabricates a computed value --- the agent produces a
plausible but incorrect result.
\textbf{FM-2.5} corrupts an input before the agent processes it ---
the agent uses a stale or tampered value.
Business-logic faults (BL-*) corrupt domain-specific fields such as
charge amounts, email recipients, product lists, or carrier selections.
Each operator is judged at the first LKW checkpoint where the
mutated value becomes observable.

\section{Experimental Setup}
\label{sec:experimental-setup}

\subsection{Compute Environment}
Runs are executed on Concordia SPEED HPC with dedicated compute allocation.
Runtime is controlled via timeout, retry, token, and iteration limits to reduce
variance. The ShippingService Retail-bench campaign uses an NVIDIA A100-SXM4-80GB
in MIG mode (1g.20gb slice, 20\,GB VRAM) with \texttt{qwen2.5-coder:14b} (9\,GB
model weight, full GPU inference via Ollama).

\subsection{Three-Baseline Experimental Structure}
\label{sec:baselines}

The study uses three baselines that correspond to three distinct roles in the
mutation analysis:

\begin{description}
  \item[\textbf{B1 --- Oracle (specification)}] The deterministic microservice
        behaviour captured by running each agent with \texttt{USE\_LLM=false}
        and gRPC dependencies replaced by controlled mocks. B1 is not a
        runtime experiment --- it is the \emph{specification} of correct agent
        behaviour. The ground-truth value of every agent state variable at
        every LKW observation point is recorded from B1 runs and used as the
        reference for all equivalence comparisons.

    \item[\textbf{B2 --- Natural variance baseline}] The same agent running with
      \texttt{USE\_LLM=true} (live LLM inference), \emph{no fault injection}.
        B2 captures how far the LLM-generated output naturally deviates from
        B1 across repeated runs. The detection envelope --- how much deviation
        from B1 is normal --- is calibrated exclusively from B2 data, prior to
        any B3 analysis. Equivalence relations are fixed from B2 to prevent
        contamination of fault evidence by natural variance.

    \item[\textbf{B3 --- Fault injection}] The same agent with
      \texttt{USE\_LLM=true} and a single mutation operator active.
        A B3 trace is a \emph{detected fault} (classically: killed mutant) if
        its LKW deviation from B1 exceeds the B2 envelope; it is an
        \emph{undetected fault} (classically: live mutant) if the fault's
        fingerprint hides within natural variance.

        \textbf{Terminology note.} We adapt the mutation testing metaphor: each
        injected fault is treated as a mutant operator, and a fault is
        ``killed'' if the LKW checkpoint evidence shows deviation from the B1
        oracle beyond the B2-derived threshold. This measures
        \emph{fault detection rate} --- how robustly the system's observable
        state reflects injected failures --- rather than test-suite adequacy in
        the classical sense. The B3 kill rate is therefore equivalent to the
        fault detection rate for the given agent and fault mode. The ShippingService
        Retail-bench and Google-bench campaigns
        (Sections~\ref{sec:google-bench} and~\ref{sec:retail-bench}) report
        B3 results. The six-agent deterministic runs
        (Section~\ref{sec:b1-oracle}) report B1. B2 natural variance has been
        collected for the full pipeline (seven agents, three
        \texttt{qwen2.5:3b} temperature configurations, 30 runs) and for
        standalone agents (nine agents, 212 runs, up to four model
        configurations). The B2 false positive rate is \textbf{0.0\%} across
        all agents and configurations: no clean \texttt{FAULT\_MODE=NONE} run
        was misclassified as infected, confirming that B3 kill verdicts reflect
        genuine fault-induced deviations rather than natural LLM variance.
\end{description}

Figure~\ref{fig:b123-protocol} summarises the logic of the three-baseline
evaluation. B1 fixes the reference behaviour, B2 defines the acceptable
live-LLM envelope around that reference, and B3 converts a faulty run into a
killed, live, or inconclusive mutant verdict by comparing it against the
B1 oracle under the B2-derived threshold.

\includegraphics[width=0.94\textwidth]{figures/fig_b123_protocol.pdf}
\caption{Three-baseline evaluation logic used throughout the study. B1 records
  the deterministic oracle trace, B2 measures live-LLM natural variance with

a mutant is judged killed.

\subsection{Execution Protocol}
\begin{enumerate}
  \item Run NONE baseline for each scenario pair.
  \item Run one fault mode at a time.
    \item Repeat for full-pipeline Google-bench (\texttt{qwen2.5:3b}, three
      temperatures), full-pipeline Retail-bench
      (\texttt{qwen2.5-coder:14b}), and standalone checkout-agent runs.
  \item Mark timeout traces as INCONCLUSIVE; rerun where feasible.
\end{enumerate}

\subsection{Agent Execution Modes}

\begin{itemize}
  \item \textbf{B1 deterministic execution}: direct calls to agent business
    logic establish the oracle values recorded at each LKW checkpoint.
    This path isolates the intended microservice behaviour from LLM routing
    variance and supplies the specification used by all equivalence checks.
  \item \textbf{Standalone live-LLM agents}: the checkout-path agent roles
    (currency, payment, email, shipping\_quote, ship\_order) are executed
    individually with Ollama-backed ReAct orchestration. This mode is used
    to study single-agent B2 natural variance and local B3 mutant
    sensitivity at the agent boundary. Product catalog already participates in
    the full checkout pipeline, while recommendation and ad service standalone
    live-agent runs are treated as follow-on evidence rather than part of the
    currently reported summary table.
  \item \textbf{Full checkout pipeline}: product catalog, currency,
    shipping, payment, and email are exercised together under a single
    checkout orchestrator. This mode is used to study end-to-end mutation
    score, infection location, and downstream business propagation under
    realistic multi-agent composition.
\end{itemize}

\subsection{Instrumentation and Structural Fixes}
During the study, two structural issues were identified and resolved. First,
the shipping agent and service files were co-located in a single directory
(\texttt{shippingservice/}), whereas every other service in the system maintains
a dedicated agent folder (e.g., \texttt{paymentagent/}, \texttt{cart-agent/}).
This co-location caused fault-injection hooks to share scope with the gRPC
service layer, blurring the agent/service propagation boundary. The agent logic
was reorganised into a dedicated \texttt{shippingagent/} module, restoring the
separation pattern used by all other services.

Second, HITL intervention points were initially identified by manual trace
inspection. To remove this bottleneck, we implemented \texttt{hitl\_detector.py},
an automated classifier that parses LKW checkpoint evidence files and assigns
each fault scenario to one of the three intervention tiers defined in
Section~\ref{sec:rq4}. The detector confirmed all scenario classifications
without manual inspection.

\section{B1 Oracle Specification: Deterministic Agent Baselines}
\label{sec:b1-oracle}
% ═════════════════════════════════════════════════════════════════════════════

\paragraph{Benchmark legend.}
All agents in this section are from the \textbf{Google Boutique} benchmark
unless explicitly marked \textbf{(RetailBen)}. Google Boutique agents:
CurrencyAgent, PaymentAgent, EmailServiceAgent, ProductCatalogAgent,
RecommendationAgent, AdServiceAgent.
RetailBen agents: ShippingQuoteAgent, ShipOrderAgent.
This labeling convention is used throughout all results sections.

To enable fault detection analysis, the B1 oracle must first be established: the
ground-truth LKW trace of each agent state variable under correct,
deterministic behaviour with no mutation operator active. We run each of
the six Python-based agents with \texttt{USE\_LLM=false} and gRPC dependencies
replaced by controlled mocks. \emph{These runs do not report fault detection
results} --- they capture the expected value of every guarded variable at
every observation point, establishing the B1 reference fingerprint against
which B3 mutation runs are compared (see Section~\ref{sec:baselines}).

For each injected mutation operator, the subsections below document the
resulting LKW trace deviation from B1. A mutation that shifts any observation
point outside the B2-calibrated equivalence tolerance is a \emph{killed
mutant}; one whose trace remains indistinguishable from natural variance is
a \emph{live mutant} (undetected by the current test suite).
For PaymentAgent \texttt{BL-AMOUNT-TAMPER}, the B3 trace deviates at
\texttt{CHARGE\_DONE}: \texttt{charged=9999.00} vs.\ B1 baseline \texttt{9.00},
with \texttt{tampered=True} set --- all steps reached (depth~=~0), confirming
a Tier~3 silent killed mutant detectable only by payload comparison.

This verdict illustrates the key decision rule used throughout the study: a
B3 trace is only treated as a genuine killed mutant when its deviation from
the B1 oracle falls clearly outside the B2 natural-variance envelope, rather
than reflecting ordinary live-LLM run-to-run fluctuation.

Across the six deterministic agents, the B1 oracle campaigns reveal a highly
consistent fault structure. Payment and Currency expose the clearest numeric
corruption signatures at \texttt{CARD\_VALIDATED}, \texttt{CHARGE\_DONE}, and
\texttt{CONVERT\_DONE}; Email, ProductCatalog, Recommendation, and AdService
show the same logic for semantic payload corruption, identity misrouting, and
silent business-rule violations. The shared conclusion is that FM-3.1 is the
only class that reliably removes downstream steps, whereas FM-2.2 and the
silent business-logic corruptions preserve the full step sequence and must
therefore be detected by checkpoint-level semantic comparison against the B1
oracle. The full per-agent fault grids are omitted from the main paper for
space because the compact cross-agent summaries already carry the result-level
evidence used in the paper's claims.

For reference, the injection flags recorded at each LKW checkpoint are:
\texttt{premature\_termination} (FM-3.1),
\texttt{hallucinated} (FM-2.2),
\texttt{amount\_tampered} / \texttt{rate\_manipulated} / \texttt{query\_tampered}
/ \texttt{context\_tampered} for FM-2.5 data-corruption variants, and
\texttt{validation\_bypassed} / \texttt{currency\_swapped} / \texttt{action\_swapped}
for FM-1.2 routing variants.
Agent-specific business-logic flags include
\texttt{save\_skipped}, \texttt{double\_charge}, \texttt{card\_declined}
(PaymentAgent);
\texttt{rate\_manipulated}, \texttt{stale\_rate}, \texttt{unavailable}
(CurrencyAgent);
\texttt{send\_skipped}, \texttt{corrupted}, \texttt{wrong\_customer}
(EmailAgent);
\texttt{price\_manipulated}, \texttt{products\_missing}, \texttt{duplicated}
(ProductCatalogAgent);
\texttt{empty\_recs}, \texttt{injection}, \texttt{self\_rec}
(RecommendationAgent); and
\texttt{empty\_ads}, \texttt{injected}, \texttt{wrong\_url}
(AdServiceAgent).
Each flag is set to \texttt{True} by the injection function at the infected
checkpoint; the B3 analyser compares against the B1 oracle value of
\texttt{False}.

\section{RQ4 --- HITL Tier Classification}
\label{sec:hitl}
% ═════════════════════════════════════════════════════════════════════════════

\textbf{Experiment Design.}
All 57 injected fault scenarios across seven agents are classified into
intervention tiers using the automated \texttt{hitl\_detector.py} classifier,
which parses LKW checkpoint evidence files without manual inspection.

\textbf{Measurement/Metrics.}
Tier assignment (Tier~1/2/3) per scenario; distribution of scenarios across
tiers; automated classification runtime.

\textbf{Answer.}
All 57 scenarios are classifiable mechanically from LKW evidence in under
one second. Distribution: 8 Tier~1 (structural), 34 Tier~2
(flag-detectable), 7 Tier~3 (silent) --- full details in Section~\ref{sec:rq4}.

Detailed tier definitions and aggregate distribution follow.

\subsection{Tier Definitions}

\begin{description}
  \item[Tier~1 --- Structural] Fault causes step loss ($\mathrm{PropagationDepth} > 0$).
        Detectable from step-count diff alone; no semantic analysis required.
  \item[Tier~2 --- Flag-Detectable] All steps reached; a boolean operational
        flag (e.g., \texttt{amount\_tampered}, \texttt{hallucinated}) is set in
        LKW checkpoint data. Requires a flag monitor or alert rule.
  \item[Tier~3 --- Silent] All steps reached; no diagnostic flag distinguishes
        the faulty trace from the clean baseline. Requires semantic validation
        of checkpoint data contents against expected ranges or schemas.
\end{description}

\section{RQ5 --- Fault Injection Stability}
\label{sec:stability}
% ═════════════════════════════════════════════════════════════════════════════

\textbf{Experiment Design.}
Each of the six deterministic Google Boutique agents' complete fault-mode
suites is executed three independent times under identical conditions.
LKW checkpoint fingerprints (infection point, steps reached, steps lost,
propagation depth) are compared across all three runs.
For RetailBen ShippingService, per-fault-mode evidence from the
\texttt{qwen2.5-coder:14b} campaign confirms stable traces for each fault mode.

\textbf{Measurement/Metrics.}
Stability label per fault mode (STABLE\_PASS, STABLE\_FAULT, UNSTABLE);
fraction of fault modes with identical LKW fingerprints across all 3 runs;
mean detection rate $\pm$ std across 3 runs per fault mode.

\textbf{Answer.}
100\% of fault modes are STABLE\_FAULT or STABLE\_PASS; std\,=\,0.00 across
all runs. No UNSTABLE entries --- full details in Section~\ref{sec:rq5}.

A central threat to construct validity in any fault injection study is
non-determinism: if re-running the same injected fault produces a different LKW
fingerprint, the evidence cannot be treated as reproducible. To address this, we
executed each of the six deterministic agents' complete fault-mode suites three
times independently under identical conditions and compared the LKW checkpoint
fingerprints (infection point, steps reached, steps lost, propagation depth)
across all three runs. For ShippingService, per-fault-mode evidence files
from the \texttt{qwen2.5-coder:14b} Retail-bench campaign confirm stable LKW
traces for each fault mode.

\subsection{Stability Classification}

Each fault mode is assigned one of three stability labels:
\begin{itemize}
  \item \textbf{STABLE\_PASS}: Baseline (\texttt{FAULT\_MODE=NONE}). All three
        runs produce an identical fault-free fingerprint.
  \item \textbf{STABLE\_FAULT}: An injected fault mode. All three runs produce
        bitwise-identical LKW fingerprints. Fault behaviour is repeatable and
        publishable.
  \item \textbf{UNSTABLE}: At least one run differs from the other two.
\end{itemize}

\begin{enumerate}

        and detection requires semantic validation of checkpoint data contents.
\end{enumerate}

\medskip
\noindent\rule{\linewidth}{0.5pt}

contracts} at every agent boundary.

\section{Boundary Validation Contracts}
\label{sec:boundary}
% ═════════════════════════════════════════════════════════════════════════════

To address the gap identified in Section~\ref{sec:cross-agent}, we implement
\emph{boundary contracts} at every inter-agent handoff in the LLM-MAS
architecture. Each contract specifies the expected payload schema and value
constraints; at runtime, a \texttt{boundary\_contract(name, expected, observed)}
call compares the actual handoff payload against the contract and emits a
\texttt{BOUNDARY\_CHECK} checkpoint into the LKW trace when a violation is
detected.

\subsection{Implementation}

The shared \texttt{boundary\_validation.py} module computes four fields for
every boundary call regardless of alert status:
\begin{itemize}
  \item \textbf{difference} --- structural delta between expected and observed
        (missing keys, extra items, field mismatches, or numeric delta).
  \item \textbf{violations} --- list of typed violation records (e.g.,
        \texttt{predicate\_failed}, \texttt{extra\_items}).
  \item \textbf{alert} --- \texttt{True} iff any violation is found or
        expected $\neq$ observed.
  \item \textbf{recovery} --- the policy decision from
        \texttt{boundary\_recovery.py} (see Section~\ref{sec:recovery}).
\end{itemize}

\subsection{Cross-Agent Boundary Evidence}

The two FM-2.2 cross-agent chains now produce explicit boundary evidence. For
Currency$\to$Payment, the contract expects 9~EUR but observes 1{,}337~EUR and
emits a positive alert with $\delta = 1{,}328$. For
Catalog$\to$Recommendation, the contract expects \texttt{PROD-001} but
observes an empty list, again producing an alert. In both cases, the
downstream agents remain structurally correct, which confirms that semantic
handoff validation is necessary even when single-agent LKW traces look normal.

Both chains that were previously Tier~3 (silent) now emit explicit boundary
alerts in the LKW trace, providing machine-readable evidence of the semantic
violation at the exact handoff point.
The downstream agents remain structurally correct (all steps reached,
\texttt{infection\_point=None}), confirming the finding that single-agent
tracing alone is insufficient.

\section{RQ6 --- Policy-Based Boundary Recovery}
\label{sec:recovery}
% ═════════════════════════════════════════════════════════════════════════════

\textbf{Experiment Design.}
A policy-based recovery pipeline is implemented on top of the boundary
contract layer (Google Boutique). For each inter-agent handoff, a
\texttt{boundary\_contract()} call evaluates the upstream agent's output
and triggers a recovery action before propagation. 19 boundary checks are
wired across 6 agent pairs.

\textbf{Measurement/Metrics.}
Number of boundary checks passing (\texttt{test\_recovery\_wiring.py});
HITL burden before vs.\ after recovery (fraction of Tier~3 faults requiring
raw payload inspection); recovery action distribution
(block / fallback / retry / continue).

\textbf{Answer.}
19/19 boundary checks pass. 2 cross-agent Tier~3 faults (Currency$\to$Payment,
Catalog$\to$Recommendation) no longer require human payload inspection ---
they now emit a structured \texttt{RECOVERY\_ACTION} record instead.
HITL burden for boundary-instrumented Tier~3 faults reduced from
``inspect raw payload'' to ``review structured record''.
Full answer in Section~\ref{sec:rq6}.

Section~\ref{sec:boundary} established that boundary contracts make silent
handoff failures observable. This section presents the third layer of the
contribution: a \emph{policy-based recovery pipeline} that turns each boundary
alert into an automatic corrective action before the violation propagates.
The complete pipeline operates in three stages: (1)~LKW+RIP detects and
classifies the fault into a HITL tier; (2)~\texttt{boundary\_contract()} emits
a \texttt{BOUNDARY\_CHECK} record and invokes the recovery policy decision;
(3)~the agent's wired recovery action executes before any unsafe downstream
code runs.

\subsection{Design}

The \texttt{boundary\_recovery.py} module implements
\texttt{decide\_recovery(boundary\_result)}, which is invoked automatically
inside \texttt{boundary\_contract()} for every handoff. The recovery decision
uses one of four actions: \texttt{continue}, \texttt{block\_and\_request\_hitl},
\texttt{fallback\_to\_last\_known\_good}, and \texttt{retry\_current\_step}.

\subsection{Recovery Policies}

The recovery logic is intentionally policy-driven. Financial and user-facing
integrity violations are blocked and escalated via
\texttt{block\_and\_request\_hitl}; catalog, carrier, and advertising
violations are corrected with \texttt{fallback\_to\_last\_known\_good}; and
quote-selection mismatches trigger \texttt{retry\_current\_step}. Unknown
boundary failures are handled fail-safe by blocking execution and requesting
human review.

\subsection{Complete Agent Wiring}

All seven agents are wired into this policy layer at the same abstraction
boundary: the handoff between a validated upstream result and a downstream
action that could amplify risk. Payment and Email block before the unsafe side
effect occurs, Recommendation and ProductCatalog replace invalid handoff data,
AdService drops injected advertising payloads, and Shipping retries or falls
back depending on whether the mismatch affects quote selection or carrier
tracking.

\subsection{Verification}

All six recovery paths were verified by an automated test suite
(\texttt{test\_recovery\_wiring.py}) executed on 2026-07-13. The suite drives
each agent directly with a forced boundary mismatch and asserts that the
recovery action is applied before any unsafe operation. All 19 checks passed,
including the key safety properties used in the paper narrative: blocking the
Currency$\to$Payment overcharge before charge execution, filtering phantom
catalog IDs before recommendation, dropping injected ads before response
assembly, and preventing corrupted email content from reaching the gRPC send
client.

\subsection{Updated HITL Tier Semantics}
\label{sec:tier-semantics-update}

The recovery layer changes the operational meaning of Tier~2 and Tier~3 for
boundary-instrumented handoffs:

\begin{itemize}
  \item \textbf{Tier~3 (silent FM-2.2), after recovery}: a
        \texttt{BOUNDARY\_CHECK} alert fires at the handoff; an automatic
        \texttt{block} or \texttt{fallback} action is applied before downstream
        execution continues. The human reviewer reads a structured
        \texttt{RECOVERY\_ACTION} checkpoint in the LKW trace rather than
        having to detect the anomaly from raw payload contents.
  \item \textbf{Tier~2 (flag-detectable), after recovery}: the flag monitor is
        supplemented by automatic policy execution. The human reviews whether
        the corrective action was appropriate, not whether a fault occurred.
\end{itemize}

The recovery layer does \emph{not} eliminate human oversight for high-risk
decisions: \texttt{block\_and\_request\_hitl} is designed to require human
sign-off. It removes the manual anomaly-detection step, not the
decision-authority step.

\subsection{Answer to RQ6}

Yes. Policy-based boundary recovery reduces the manual intervention burden
for Tier~2 and Tier~3 violations by converting detection events into automatic
corrective actions. Of the 7 previously Tier~3 (silent) FM-2.2 faults, the 2
instrumented cross-agent variants now receive \texttt{block} or \texttt{fallback}
actions that prevent unsafe execution from continuing. The remaining 5 Tier~3
cases (single-agent hallucination with no inter-agent handoff in scope) require
additional boundary contracts to be defined.

\section{Limitations}
\label{sec:limitations}
% ═════════════════════════════════════════════════════════════════════════════

\subsection{L1 --- Live-LLM Coverage Is Asymmetric Across Evaluation Modes}

The live-LLM evaluation is strongest for the checkout workflow, where both
full-pipeline B3 campaigns and standalone agent-level runners were executed.
For the broader service portfolio, coverage is asymmetric: some claims are
grounded in deterministic B1 oracle runs, some in standalone live-LLM agent
execution, and some in full checkout orchestration. The paper therefore uses
the full-pipeline mutation score and cross-agent propagation results as its
primary LLM-in-the-loop evidence, while treating per-agent measurements as a
supporting decomposition of the same phenomenon rather than as the only source
of evidence.

\subsection{L2 --- Compliance-Ambiguity Fault Remains INCONCLUSIVE}

The BL-COMPLIANCE\_AMBIGUITY fault mode remains INCONCLUSIVE at both model
scales tested. Under \texttt{llama3.2:1b}, the ReAct loop exhausted 4 iterations
without resolving the unknown compliance jurisdiction. Under
\texttt{qwen2.5-coder:14b}, the LLM inference call exceeded the 120\,s HTTP read
timeout after 577\,s of elapsed time, producing 3 missing steps
(\texttt{QUOTE\_DONE}, \texttt{CARRIER\_DONE}, \texttt{TRACKING\_DONE}). The
fault cannot be classified as TP, FN, or FP with the current timeout
configuration. Increasing the Ollama read timeout or using a GPU with higher
throughput may allow the model to complete within the window.

\subsection{L3 --- Known Instrumentation Defect in FM-3.1 Depth Calculation}

For ShippingService FM-3.1, the RIP depth calculator reports \texttt{depth=1}
(only \texttt{CARRIER\_DONE} missing) because \texttt{ESCALATION\_CHECK} was
not included in the expected-steps set. In the qwen2.5-coder:14b run,
\texttt{ESCALATION\_CHECK} is also absent from the trace, so the true
propagation depth is~2. This is a code-level instrumentation defect in the
expected-steps definition, not a model error. The classification (Partial TP)
is unaffected; only the reported depth is undercounted by~1.

\subsection{L4 --- Human Cross-Validation Pending}

The human assessment rubric has been distributed to two independent assessors.
Inter-rater agreement scores will be computed after all three assessments are
submitted. Results in this paper reflect a single assessor's evaluation.

\subsection{L5 --- Boundary Contract Coverage Scope}

The boundary contract layer instruments seven inter-agent handoff points.
The full LLM-MAS architecture contains additional service-to-service
communication paths (e.g., CartService$\to$CheckoutService, written in Go;
frontend-to-backend gRPC calls) that are not instrumented.
Tier~3 (silent) faults that propagate through uninstrumented boundaries
will not be detected by the current boundary contract layer.
Boundary coverage in this evaluation is therefore defined over the
instrumented inter-agent handoffs studied here, including the Python agent
boundaries that carry the main checkout-path fault signals.

\subsection{L6 --- ShippingAgent Recovery Wiring Scope}

The ShippingAgent's recovery wiring covers the \texttt{carrier\_to\_tracking}
and \texttt{quote\_to\_carrier} boundaries but does not include a
\texttt{SAVE\_DONE} fallback. Persistence-layer faults (FM-1.2,
BL-SHIPMENT\_LOST) for the ShippingAgent are therefore not covered by the
recovery layer. Full wiring requires implementing a \texttt{retry\_current\_step}
or compensating transaction at the \texttt{SAVE\_DONE} boundary, which would
require MongoDB write-path coordination beyond the recovery surfaces evaluated
in this study.

\section{Cross-Benchmark Analysis}
% ═════════════════════════════════════════════════════════════════════════════

\subsection{RQ1: Reproducibility of Fault Injection}
Controlled injection is reproducible for all fault modes in the six deterministic
agents (100\% stability, 54 mode-runs $\times$ 3 repetitions). For the
ShippingService Retail-bench, all fault modes except BL-COMPLIANCE\_AMBIGUITY
produce consistent, observable fault traces under \texttt{qwen2.5-coder:14b}.
BL-COMPLIANCE\_AMBIGUITY remains INCONCLUSIVE at both model scales tested due
to inference timeout (see Limitation~L2).

\subsection{RQ2: First Failure Appearance}
Across scenarios, infection first appears at:
\begin{itemize}
  \item \texttt{CARRIER\_DONE} for hallucination and ignored-input faults
        (FM-2.2, FM-2.5, BL-VENDOR\_NEGOTIATION),
  \item \texttt{QUOTE\_DONE} for cost corruption faults
        (BL-REFUND\_REASONING, BL-INVENTORY\_MISMATCH) and FM-3.1 (ShippingService),
  \item \texttt{SAVE\_DONE} for persistence-loss and incomplete-path faults
        (BL-SHIPMENT\_LOST, FM-1.2),
  \item \texttt{ESCALATION\_CHECK} for post-agent policy faults
        (BL-CUSTOMER\_ESCALATION).
\end{itemize}

\subsection{RQ3: Downstream Propagation}
Propagation depth is highest when structural steps are skipped: FM-3.1 and
FM-1.2 each lost 2--3 downstream checkpoints, and BL-SHIPMENT\_LOST removed
\texttt{SAVE\_DONE} entirely. In contrast, semantic corruption faults (FM-2.2,
FM-2.5, BL-VENDOR\_NEGOTIATION, BL-REFUND\_REASONING) completed all checkpoints
with propagation depth zero, meaning corruption was carried forward silently
rather than disrupting the step sequence.

\subsection{RQ4: Auto-Resolution vs.\ Human Intervention}
\label{sec:rq4}

We classify the scenarios into three intervention tiers:

\begin{itemize}
  \item \textbf{Tier~1 --- Structurally disruptive or workflow-stopping}:
        FM-3.1, FM-1.2, BL-SHIPMENT\_LOST, and BL-COMPLIANCE\_AMBIGUITY (if
        resolved). All require human or architectural intervention.

  \item \textbf{Tier~2 --- Detectable via metadata flags}:
        BL-CUSTOMER\_ESCALATION, BL-INVENTORY\_MISMATCH, BL-VENDOR\_NEGOTIATION,
        BL-REFUND\_REASONING. These require a human-readable flag monitor or
        downstream invariant check.

  \item \textbf{Tier~3 --- Silently absorbed}: FM-2.2 (hallucinated output)
        and FM-2.5 (stale cost). These carry the highest latent business risk
        and require checkpoint-data inspection rather than step-sequence
        monitoring.
\end{itemize}

\texttt{hitl\_detector.py} confirmed all tier classifications mechanically from
LKW checkpoint evidence files in under one second.

\subsection{RQ5: Stability Across Repeated Runs}
As reported in Section~\ref{sec:stability}, all 64 mode-runs across all seven
agents produced identical outcome classes with zero UNSTABLE entries (100\%
stability rate). For the six deterministic agents, 54 mode-runs $\times$ 3
repetitions yield 162 total individual runs without a single non-deterministic
outcome. For ShippingService, per-fault-mode evidence files confirm stable LKW
traces for each of the 10 assessed fault modes under
\texttt{qwen2.5-coder:14b}.

\subsection{RQ6: Policy-Based Recovery and HITL Burden Reduction}

Yes, with scope qualifications. Of the 57 injected fault scenarios, 7 are
Tier~3 (silent). The 2 cross-agent Tier~3 cases (Currency$\to$Payment FM-2.2,
Catalog$\to$Recommendation FM-2.2) now receive automatic
\texttt{block} or \texttt{fallback} recovery actions via boundary contracts,
confirmed by 19/19 checks in \texttt{test\_recovery\_wiring.py}.
These 2 scenarios no longer require a human to inspect raw payload contents
to detect the anomaly --- the \texttt{RECOVERY\_ACTION} LKW record provides
machine-readable evidence of the corrective action taken.

The remaining 5 Tier~3 cases are single-agent hallucinations with no
inter-agent handoff currently in scope; they require additional boundary
contracts to be defined before recovery applies. The full answer to RQ6 is
therefore: \emph{policy-based recovery reduces the HITL burden for
boundary-instrumented Tier~3 faults from ``detect from raw payload'' to
``review structured RECOVERY\_ACTION record''; it does not reduce the burden
for Tier~3 faults that occur within a single agent without a boundary handoff.}

\subsection{RQ7: Failure Attribution Validation (AgenTracer Pipeline)}
\label{sec:rq7}

We validate our LKW+RIP attribution methodology against the AgenTracer
framework~\cite{zhang2025agentracer}, which frames failure attribution as
identifying the ground-truth pair $(i^*, t^*)$: the error agent and the
decisive fault step. We implemented two attributors over all 60 evaluated
trajectories (54 single-agent + cross-agent chains) using our
\texttt{agentracer\_adapter} pipeline.

\textbf{Rule-Based Attributor} (deterministic, using LKW tier/flag evidence):
agent-level accuracy \textbf{98.3\%} (59/60), step-level accuracy
\textbf{63.3\%} (38/60).

\textbf{LLM-Based Attributor} (\texttt{qwen2.5:3b} prompt attribution via
Ollama on SPEED HPC): agent-level accuracy \textbf{96.7\%} (58/60),
step-level accuracy \textbf{5.0\%} (3/60).

Per-agent rule-based accuracy is 100\% for all six agents except
CurrencyAgent (88.9\%, 8/9). The single miss is the Tier~3 silent case where

boundary contracts change the observable fault signature.

The 5\% LLM step accuracy reveals that \texttt{qwen2.5:3b} reliably identifies

that their fine-tuned model weights are not yet released~\cite{zhang2025agentracer};
swapping the prompt-based LLM call for the released weights is the intended
next step and is supported by the \texttt{\_llm\_call()} hook in
\texttt{attributor.py}.

\section{Threats to Validity}
% ═════════════════════════════════════════════════════════════════════════════

\begin{itemize}
  \item \textbf{LLM scope}: the six deterministic agents bypass LLM inference;
        the tier classifications and stability results for those agents reflect
        framework correctness, not LLM detection capability (see Limitation~L1).
  \item \textbf{Runtime instability}: HPC queue and node load can affect
        inference latency; controlled timeout limits mitigate variance but do
        not eliminate it, as evidenced by the BL-COMPLIANCE\_AMBIGUITY timeout.
  \item \textbf{Model behaviour variance}: single-pass completion and output
        formatting drift in \texttt{qwen2.5-coder:14b} may require updated
        injection fallbacks for future model versions.
  \item \textbf{Instrumentation coupling}: some infections require final-answer
        normalisation fallbacks to remain observable, introducing a partial
        dependency between injection and observation layers.
  \item \textbf{Coverage scope}: fault injection is currently implemented for
        the ShippingService and six Python-based agent services; two additional
        agents written in Go and C\# remain untested, limiting generalisability
        of the tier classifications.
  \item \textbf{External validity}: results from these benchmarks may not
        fully generalise to agent architectures with multi-pass reasoning loops
        or alternate LLM backends.
  \item \textbf{Boundary construct validity}: boundary contract alerts are
        triggered by structural mismatch (missing keys, value delta) between
        expected and observed payloads. The ``expected'' value is defined by the
        test harness at call time; in production, incorrect expected values would
        produce false-positive alerts or miss genuine violations. Boundary
        contract effectiveness depends on the quality of the caller-supplied
        expected payload.
  \item \textbf{Recovery policy generalisation}: the six recovery policies were
        designed for the specific fault modes studied. Their correctness for
        novel fault modes not covered by the current injection suite is not
        demonstrated. The catch-all \texttt{block\_and\_request\_hitl} policy
        provides a safe default but may over-escalate for benign payload
        variations.
  \item \textbf{Recovery wiring internal validity}: the
        \texttt{test\_recovery\_wiring.py} verification suite uses
        mock/stub agents and gRPC clients. Recovery wiring correctness under
        live gRPC execution with real network latency and partial failure
        conditions has not been verified.
\end{itemize}

\section{Conclusion}
% ═════════════════════════════════════════════════════════════════════════════

This paper presents a controlled fault-injection study of an agentic
microservice system across two benchmark suites and seven instrumented agent
services. The core contribution is not only a fault taxonomy or a benchmark
suite, but an execution-level methodology: B1 oracle specification, B2 natural
variance calibration, B3 mutant execution, and checkpoint-level LKW+RIP
evidence collection.

Across the deterministic oracle and repeated baseline campaigns, the
instrumentation remains reproducible and stable. In the live-LLM full checkout
pipeline, the B3 campaign kills 29 of 40 mutants (72.5\% mutation score), with
the strongest detection coming from the \texttt{qwen2.5:3b} configurations.
The comparative result is especially important: \texttt{qwen2.5-coder:14b}
often terminates the workflow in a single-pass \texttt{TASK\_START} to
\texttt{FINAL\_ANSWER} pattern, producing false negatives despite greater raw
model capacity.

Three principal findings emerge. First, FM-3.1 (premature termination) is the
only fault class that produces structural step loss across all agents, making it
automatically detectable from LKW step-count diffs (Tier~1). Second, FM-2.2
(hallucinated output) is the most dangerous single-agent fault class: it
completes all checkpoints with propagation depth zero, leaving no structural
signal --- detection requires semantic validation of checkpoint data contents
(Tier~3). Third, and most critically, FM-2.2 is also the highest-risk
\emph{cross-boundary} fault: a structurally correct downstream agent cannot
recover from upstream hallucination, producing quantifiable downstream harm
(14{,}755.6\% financial overcharge; phantom product recommendations) with no LKW
alert at either hop.

The automated HITL classifier demonstrates that tier boundaries are mechanically
computable from checkpoint data, removing the manual inspection bottleneck.
Together, these results show that inter-agent output validation contracts at
agent boundaries are a necessary architectural requirement for safe LLM-MAS
deployment, not an optional enhancement. The paper therefore argues for a
design shift in agentic microservices: trust cannot be placed in final answers
alone; it must be anchored in checkpoint-level semantic contracts at the points
where agent outputs become other agents' inputs.
